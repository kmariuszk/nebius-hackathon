Component diagram

1. The parts and how they talk

Five parts: the researcher's browser, a board service that owns each shared board, an agent harness (our AI agents), a discovery service that finds and scores papers, and external model and data APIs. The two services are separate deployments on Nebius; the models stay on Token Factory, as the brief requires.

  • The sync room is the source of truth for the canvas. Every change, from a person or an agent, lands there and is broadcast to every open browser.
  • Agents never touch the browser. They change the board only through the canvas MCP, so they work even when nobody has the board open.
  • Every capability is an MCP tool. Our harness and an external agent (Claude, Cursor) use exactly the same two MCP servers.
  • Per-viewer actions go over ACP (zoom to a card, light up cards), so they move only the asking researcher's view.

Sequence diagram

2. A discovery run, from question to filled board

Ana creates a board with a question and seed papers, then asks the agent to find related work. Cards appear as soon as the agent is confident and fill in while reader agents work in the background.

sequenceDiagram
  autonumber
  actor R as Ana (browser)
  participant B as Board service
  participant H as Harness: master
  participant S as search agents
  participant D as Discovery service
  participant M as Token Factory
  participant X as Paper sources

  R->>B: Create board, upload seeds (REST)
  R->>B: Open sync room and chat (WebSockets)
  B->>H: Spawn harness, pipe ACP to it
  R->>H: session/prompt: find related work
  H->>D: resolve_seed (papers MCP)
  D->>X: OpenAlex lookup, Parse reads PDFs
  H->>M: Plan, split question into ~3 sub-queries
  loop each sub-query, in parallel
    H->>S: search(sub-query)
    S->>D: search, find_candidates
    D->>X: PubMed MCP, OpenAlex, Semantic Scholar, Tavily
  end
  H->>D: score_candidates
  D->>M: One Lightning verdict + quote per paper, in parallel
  loop each confident paper
    H->>B: add_papers, link_papers, mark_working (canvas MCP)
    B-->>R: Card appears with "working" badge (sync, all browsers)
  end
  H->>D: rerank top ~100 (Super VL)
  H->>B: set_rating
  B-->>R: Card colours settle, ranked list updates
  H-)H: process_papers: reader + context in background
  H->>D: get_fulltext, get_figures (Parse)
  H->>B: set_summary, add_highlight, add_quote, add_figure, link_papers
  B-->>R: Card fills in, badge clears
  H-->>R: Streamed plan, tool cards and messages (ACP)
  • Steps 8 to 10 fan out: one search agent per sub-query.
  • Scoring is a tool, not an agent: the discovery service fires hundreds of Lightning calls in parallel and returns only the best.
  • Early placement means Ana sees cards within seconds, before ranking and summaries finish.
  • Solid arrows are calls, dashed arrows are replies or broadcasts, and the open arrow is work started in the background.

3. Coming back: "Catch me up"

Overnight, a daily run placed new papers on the board. Ana opens it and asks to be caught up; the agent tours the new papers and Ana triages them on the spot.

sequenceDiagram
  actor R as Ana (browser)
  participant B as Board service
  participant H as Harness: master
  participant T as Teammates' browsers

  R->>B: Open board (sync)
  B-->>R: New papers already in their clusters
  R->>H: "Catch me up" (ACP prompt)
  H->>B: Activity since Ana's last visit, get_board
  loop each new paper
    H-->>R: _canvas/focus: zoom in (Ana's view only)
    H-->>R: Explanation, streamed into chat
    R->>B: Keep or Discard (REST vote)
    B-->>R: Card status updates (sync)
    B-->>T: Same update for everyone, with Ana's avatar on the vote
  end
  H-->>R: _canvas/focus: zoom back out
  • The tour is per viewer: only Ana's view moves; teammates keep theirs.
  • Votes are shared: everyone sees Ana's Keep or Discard live, and the agent never votes itself.
  • Keep makes the paper a seed for the next run; Discard keeps it out of all later runs.

4. What the system stores

The board service owns everything about the board and its people; the discovery service owns everything about papers. They share no database: a paper card on a board points at a paper record by ID.

  • A verdict is per board: the same paper can be highly relevant to one project and irrelevant to another.
  • Every agent-made item carries who asked for it and which run made it, so a whole run can be reviewed or undone.

5. Which protocol does what

ProtocolBetweenCarries
tldraw sync (WebSocket)Browsers and the board serviceThe shared canvas: cards, links, notes, highlights, cursors
ACP (WebSocket, piped to stdio)One researcher's chat and their harnessPrompts, streamed plan and tool cards, approvals, cancel, per-viewer zoom and highlight
MCP (HTTP)Any agent and the two MCP serversEvery capability: search, scoring, reading, placing and linking papers
REST + SSEBrowser and the board serviceBoards, invites, votes, paper records, PDFs, ranked list, activity feed
